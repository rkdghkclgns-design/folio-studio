# 메모리 사용을 제한한 테스트 실행

현재 `npm test`는 아래 명령으로 전체 `*-tests.mjs` 파일을 실행합니다.

```sh
node --max-old-space-size=512 --test --test-concurrency=1 *-tests.mjs
```

`--test-concurrency=1`은 동시에 실행하는 테스트 파일 수를 하나로 제한합니다. 각 테스트가 별도로 시작하는 작업이나 외부 프로세스까지 모두 하나로 만드는 옵션은 아닙니다. [Node.js 테스트 동시 실행 옵션](https://nodejs.org/api/cli.html#--test-concurrency)

`--max-old-space-size=512`는 V8의 old-space 상한을 **512MiB**로 설정합니다. 전체 프로세스의 RSS, 네이티브 버퍼, 젊은 세대 힙, 운영체제 메모리를 합친 512MiB 상한이 아닙니다. 테스트 실행기의 부모 프로세스와 테스트 파일 프로세스도 각각 메모리를 사용합니다. 한도에 가까워지면 가비지 컬렉션 부담이 커질 수 있습니다. [Node.js 힙 크기 옵션](https://nodejs.org/api/cli.html#--max-old-space-sizesize-in-mib)

## 오류를 좁혀 확인하는 순서

1. 실패한 파일 하나를 같은 제한으로 실행합니다.
2. 재현되는 오류 메시지와 실패 지점을 확인하고, 큰 객체 비교나 남은 비동기 작업을 조사합니다.
3. 수정한 파일의 검사가 통과하면 `npm test`를 한 번 실행합니다.
4. 앱 전체 검사와 별도로 연결 도우미 검사, EPUBCheck, 실제 브라우저 확인을 수행합니다.

```sh
node --max-old-space-size=512 --test --test-concurrency=1 book-editor-tests.mjs
npm test
python -m unittest discover -s companion -p 'test_*.py'
npm run validate:epub
```

전체 스위트를 여러 터미널에서 동시에 실행하지 않습니다. 이미 실행 중인 테스트가 있으면 결과를 기다리며, 필요 없는 중복 프로세스를 만들지 않습니다. `--test-force-exit`로 남은 타이머 문제를 숨기는 대신 종료 처리를 고칩니다.

## 큰 실패 출력과 DOM 수명 관리

실패한 `assert.equal()`이나 `assert.deepEqual()`이 수십만 자 원고, base64 이미지 또는 전체 DOM 객체를 비교하면 진단용 차이를 만들고 출력하는 과정도 부담이 될 수 있습니다. 검증 범위를 줄이는 대신 결과를 간결하게 표현합니다.

이번 검증에서는 수정 이전에 시작된 `redteam-ui` 포커스 검사의 DOM 객체 비교가 실패한 뒤 약 110초 동안 차이 출력 생성에 머무는 병목을 직접 확인했습니다. 객체 동일성은 `assert.ok(actual === expected, '포커스 대상이 일치해야 함')`처럼 확인하면 조건을 유지하면서 전체 DOM 차이 출력을 피할 수 있습니다. 이 관측이 최초 Windows 오류 1455의 단일 원인을 확정하는 것은 아닙니다.

- 긴 원고는 길이·해시·핵심 경계 조건을 나누어 확인합니다. 전체 동일성을 확인할 때도 오류 메시지에 원고 전체를 포함하지 않습니다.
- 이미지 데이터나 책 JSON을 통째로 로그에 출력하지 않습니다. 크기, 항목 수, 식별자와 해시를 기록합니다.
- DOM 객체 자체를 비교하는 대신 필요한 텍스트·속성·역할·데이터를 비교합니다.
- 각 테스트에서 편집기와 뷰어의 `destroy()`를 호출하여 이벤트 리스너, 이미지 로딩, 관찰자와 타이머를 해제합니다.
- happy-dom의 예약 작업을 중단하고 창을 닫습니다. 비동기 테스트가 만든 Promise와 실제로 필요한 저장 작업은 완료 또는 취소 상태를 확인합니다.
- 가짜 타이머를 사용했다면 원래 타이머를 복원합니다. 테스트 간 전역 상태도 정리합니다.

이 항목들은 메모리 압박과 종료 지연을 줄이기 위한 운영 기준입니다. 과거의 모든 중단이 위 원인 때문이었다고 확정한 것은 아닙니다. 정확한 원인 분석에는 해당 실행의 로그와 프로세스별 메모리 관측이 필요합니다.

## 이번 PC의 관측과 판단

2026-10-20 점검 시 보고된 값은 다음과 같습니다. 실행 중인 프로그램에 따라 달라지는 시점별 관측입니다.

| 항목 | 관측값 |
| --- | --- |
| 설치 RAM | 약 32GB |
| 사용 가능한 물리 메모리 | 약 21.5GB |
| 페이지 파일 | 자동 관리, 약 62GB |
| 시스템 커밋 사용 비율 | 약 29% |

이 값만으로 RAM 증설이나 페이지 파일 확대가 필수라고 판단할 근거는 없습니다. 현재 테스트의 동시 실행 수, 객체·DOM 수명과 실패 출력부터 관리합니다. 이번 작업에서는 Windows 페이지 파일이나 기타 운영체제 메모리 설정을 변경하지 않았습니다.

Windows의 커밋 한도는 물리 메모리와 페이지 파일에 영향을 받습니다. 커밋 사용량이 한도에 가까워지는지, 실제 오류 순간에 가용 RAM과 디스크 여유가 어땠는지를 함께 봐야 합니다. 페이지 파일은 커밋 여유와 크래시 덤프를 위한 기능도 있으므로 무조건 끄거나 고정된 배수로 변경하지 않습니다. [Microsoft Learn: 페이지 파일과 시스템 커밋](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/introduction-to-the-page-file)

위 운영 설정과 관측은 테스트 통과나 배포 완료의 증거가 아닙니다. 릴리스 판단에는 해당 커밋의 전체 테스트 종료 결과와 배포 작업 결과를 사용합니다.
